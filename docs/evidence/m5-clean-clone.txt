TWO DELIBERATE DEVIATIONS (both to protect a live production demo)
  1. DataHub GMS at :18080, not the quickstart's :8080.
     `datahub docker quickstart` was NOT run — local disk is nearly full and a
     DataHub v1.7.0 instance is already running remotely, reachable through an
     SSH tunnel on localhost:18080. The steward's DataHub phases were pointed at
     :18080 via DATAHUB_GMS_URL. A judge on a clean machine would run the
     quickstart and use the default :8080; everything the agent does is
     port-agnostic, so this substitutes cleanly.
  2. Connector ingest was run with --dry-run and a file sink, never a real
     ingest. Reason: the judge recipe's URNs collide with the production
     deployment's URNs; a real ingest against the live GMS would overwrite
     production metadata before the demo. --dry-run exercises the full source
     (schema discovery, row counts, containers, profiles) and skips all sink
     writes.
     Sub-deviation: DataHub constructs the sink even during --dry-run, so the
     recipe's `datahub-rest`/:8080 sink was swapped for a local `file` sink to
     guarantee zero traffic to any DataHub instance. Source config was untouched.

HONESTY NOTES (things that make this less than a perfect judge simulation)
  * This machine was already logged in to Convex (~/.convex/config.json exists).
    A true judge would not be. In practice this did not matter — see step 4;
    the CLI never asked to log in and chose an anonymous local deployment.
  * uv's package cache was warm, so the connector install took 1.9s. A judge
    downloads ~67MB of wheels; expect 1–3 minutes.
  * Steps 7 and 8 (steward, graph) write back to the GMS they are pointed at.
    Because they were pointed at :18080, this run DID write to the live
    production DataHub: four assertion run-events with judge-mode numbers, plus
    graph lineage/summary aspects. This was not anticipated when the test was
    scoped as "read-only orient". See FINDING 6.
